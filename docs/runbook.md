# Инструкция PO и эксплуатация

## Работа PO

1. Откройте реестр и выберите продуктовую тему. Счётчик — уникальные обращения, не число версий и не число пользователей. Прирост — обращения за последние 7 дней минус предыдущие 7; процентный рост без знаменателя не выдумывается.
2. Проверьте маскированные подтверждения, сценарий и неопределённости. ID источника — защищённый указатель; фактический URL исходной тикет-системы пока неизвестен и не генерируется. Доступ к первоисточнику обеспечивается корпоративной системой отдельно.
3. Исправьте заголовок и потребность, если нужно. Для split отметьте часть evidence, затем задайте новый заголовок. Для merge выберите тему того же продукта, ACL и типа. Темы, уже связанные с задачами, автоматически не объединяются.
4. Одобрите либо отклоните тему, оставив основание решения. Обновившиеся данные сбрасывают старое согласование. Конфликт версии означает, что карточку нужно перечитать.
5. Включённый rollout разрешает отдельную кнопку создания задачи **после** одобрения. Теневой режим её скрывает. Ошибка адаптера сохраняется; повтор создания безопасен при выполненном контракте идемпотентности.
6. Регулярно просматривайте «Редкие пожелания»: до 3 обращений и возраст от 30 дней. Эти пороги — настройки малого пилота в коде, должны быть согласованы. Дайджест выдаёт максимум 10 тем и помечает их включёнными в выпуск на 7 дней; сообщений поддержке не отправляет.

## Запуск и владельцы

Пилот — модульный монолит с SQLite job store. `serve` запускает worker; `worker` можно выделить, у сервера тогда `--no-worker`. Встроенный WSGI-сервер однопоточный, предназначен для локального запуска. Для корпоративного пилота нужен согласованный production WSGI server/reverse proxy, HTTPS, лимиты тела/соединений, timeout и process supervisor. SQLite подходит только для небольшого измеренного потока; при нагрузке выделить реляционную БД, очередь и outbox.

Назначить перед запуском: технического владельца, PO каждого продукта, владельца source gateway, владельца tracker gateway и ответственного ИБ/on-call. Конкретных ответственных должна определить команда до начала пилота.

## Мониторинг и сбои

`/health` проверяет HTTP liveness, не готовность интеграций. Администратор видит `/api/operations`: очередь по статусам, dead jobs, p95/max возраста необработанных обращений, `slo_at_risk` при p95 >24ч, ошибки бэклога и аудит. На пилоте подключить корпоративный сборщик к этому endpoint через авторизованную сессию/согласованный service identity adapter. Автоматическая доставка алертов пока отсутствует.

* **DLQ:** после 3 попыток задание `dead`; ошибка — только имя класса. Проверить upstream по correlation_id в защищённом контуре. После устранения нажать «Повторить» у admin. Нет текста/плохой ASR — проверить доступ и качество материала, не выдумывать содержание.
* **Worker упал:** running jobs старше 10 минут повторно доступны. Model calls происходят вне транзакции; запись результата проверяет версию источника и состояние job, поэтому параллельное обновление не возвращает старые данные.
* **Источник недоступен:** checkpoint не продвигается. После восстановления опрос повторяет окно; уникальный source/version предотвращает дубли. Контролировать API rate limit самого шлюза.
* **Трекер недоступен:** ссылка имеет sync_status=error, last_synced_at сохраняется. Status sync повторяется раз в минуту. Ошибка при создании повторяется явным одобренным вызовом PO; шлюз возвращает ту же логическую задачу по ключу. Автоматического retry создания без нового запроса сейчас нет.
* **Давление очереди:** ограничить ingestion на reverse proxy, разнести worker, измерить ASR/LLM throughput; не снимать ACL/маскирование. Точные capacity/пороги потребуют исходных объёмов.

## Retention и ИБ

* БД, WAL/SHM, резервные копии и секреты размещать на защищённом зашифрованном томе. SQLite сам по себе **не шифрует** содержимое. `umask 077`, БД 0600; закрыть каталог service account. Использовать корпоративный secret store вместо демонстрационных паролей.
* Базовое маскирование покрывает email, российские телефоны, карты, паспорт и явно подписанные ФИО/ИНН/СНИЛС/секреты. Это не полноценный DLP/NER: свободные имена, адреса, нестандартные идентификаторы требуют корпоративной политики и проверки. До неё допускаются только обезличенные данные.
* На ACL/tombstone update немедленно деактивируются evidence, обнуляется сохранённый извлечённый текст затронутого источника, перестраиваются карточки, очищается текст комментариев решений затронутых тем. Текущее содержание и счётчики недоступны по старым правам.
* TTL выполняется раз в минуту и перед авторизованными HTTP-запросами; доступ к полностью просроченной теме дополнительно запрещается независимо от worker. Удаляется производный текст, пустая карточка очищается, остаются технические ID и аудит. SQLite secure_delete включён. Физическое истечение WAL, старых резервных копий, audit IDs и уже созданных задач трекера требует согласованной политики инфраструктуры/трекера. Общекорпоративная политика ещё не утверждена.
* RBAC+ACL проверяются сервером; admin не получает автоматический доступ к закрытому содержимому. Identity — локальные аккаунты; SSO, lifecycle пользователей и централизованный rate limit нужно подключить до промышленного rollout.
* Prompt injection трактуется как текст. Модель не имеет tools/credentials для тикетов и трекера. Реальный red-team Qwen всё равно обязателен: regex/промпт не доказывают полную защиту.

## Backup, восстановление, миграция и rollback

Остановите приложение или выполните online backup через sqlite3.Connection.backup, чтобы не копировать живую БД без WAL. Пример для остановленного приложения:

```sh
python3 -c "import sqlite3; src=sqlite3.connect('data/feedback.db'); dst=sqlite3.connect('data/backup.db'); src.backup(dst); dst.close(); src.close()"
```

Проверка копии: `python3 -c "import sqlite3; print(sqlite3.connect('data/backup.db').execute('PRAGMA integrity_check').fetchone()[0])"` → `ok`. Хранить backup вне открытого доступа и применять утверждённый срок хранения; демонстрационная команда не заменяет регламент.

Схема v1 создаётся идемпотентно при запуске, версия хранится в schema_version. Up/down миграций между релизами пока нет: это первый релиз. До изменения схемы — backup, отдельная проверка миграции и restore. Rollback к v1: остановить процессы, вернуть код и совместимый snapshot БД, сначала включить SHADOW_MODE=1, сверить source checkpoint и задачи по idempotency key; только потом возобновить rollout. Восстановление может повторить чтение событий, но не должно дублировать задачи при соблюдении контракта gateway.
